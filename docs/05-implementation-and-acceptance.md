# 實作路線與驗收

## 1. 兩週建置路線

### 第 1–2 天：資料入口

- 建立 Drive 原圖資料夾與不可覆寫規則。
- 建立 Google 表單及 Meal ID。
- 建立 Meals、CGM、Analysis 三張工作表。

### 第 3–4 天：餐點結構化

- 串接多模態模型。
- 套用 `prompts/meal-vision-agent.md`。
- 實作人工確認與修正紀錄。

### 第 5–6 天：CGM 分析

- 匯入 CGM CSV。
- 驗證時區與單位。
- 執行 `scripts/analyze_cgm.py`。
- 以人工抽查驗證 5 餐計算。

### 第 7 天：端到端演練

- 從拍照到報告完整跑 10 餐。
- 記錄失敗點、修改次數與處理時間。

### 第 8–14 天：個人驗證

- 累積至少 30 餐。
- 選 2–3 類常吃主食重複測試。
- 完成至少一組單一變因控制比較。

## 2. 上線前檢核

- [ ] 原始影像與處理後資料分離。
- [ ] meal_start_at 由使用者確認。
- [ ] 所有時間包含 IANA 時區。
- [ ] 營養值以區間呈現。
- [ ] 低信心項目會觸發確認。
- [ ] CGM 計算不依賴 LLM。
- [ ] 每餐有品質類別與原因碼。
- [ ] 公開示例均為合成或去識別資料。
- [ ] 不提供診斷及藥物建議。

## 3. Go／No-Go 決策

### Go：進入 v2 App

達成 README 的主要驗收指標，且至少產生三項跨日可重複、可行動洞察。

### Iterate：留在 v1

洞察有價值，但資料缺漏、使用者修正率或時間對齊仍未達標。優先修正資料入口和確認介面。

### Stop／Pivot

即使在高品質資料下，餐點推估仍無法支援有意義分級，或使用負擔使紀錄完成率過低。此時應改採秤重、條碼、食譜或較窄的餐點類別。
